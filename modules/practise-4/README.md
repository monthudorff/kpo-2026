# Практика 4. Тестирование приложения с Dependency Injection

## Цель

Научиться строить unit, mock и интеграционные тесты для приложения из [практики 3](../practise-3/README.md). Задание не привязано к языку или фреймворку: его можно выполнить на Java, Kotlin, Go, C# и других языках.

## Исходный код

Возьмите **вариант с Dependency Injection** из практики 3. `ReportSaver` и `ReportSender` должны передаваться в `ReportService` извне, а точка запуска или DI-контейнер должна собирать объектный граф.

Не используйте вариант Service Locator как основной объект тестирования: цель практики — показать, что явные зависимости легко изолировать и подменять.

| Компонент | Ответственность |
|---|---|
| `Report` | Данные отчёта и их валидация. |
| `ReportSaver` / `TextReportSaver` | Контракт и файловое сохранение отчёта. |
| `ReportSender` / `EmailReportSender` | Контракт и имитация доставки отчёта. |
| `ReportService` | Сначала сохраняет отчёт, затем отправляет его. |
| Конфигурация DI | Регистрирует реализации и создаёт `ReportService`. |

Тесты и прикладной код должны находиться в разных исходных каталогах или модулях, если это принято в выбранной экосистеме.

## Общие правила

- Используйте фиксированные дату и время вместо системных часов.
- Один тест проверяет один сценарий и имеет понятное имя.
- Тесты не зависят от порядка запуска, сети, реальной почты или файлов из рабочего каталога.
- Все тесты запускаются одной командой выбранного инструмента.

## Часть 1. Unit-тесты

Unit-тест проверяет один компонент в изоляции. Подключите тестовый фреймворк выбранного языка и покройте модель `Report`.

Добавьте или сохраните валидацию:

- заголовок обязателен и не состоит только из пробелов;
- число проданных автомобилей неотрицательно;
- число проданных мотоциклов неотрицательно.

Напишите тесты для сценариев:

| Сценарий | Ожидание |
|---|---|
| Создание корректного отчёта | Все поля доступны без изменений. |
| Пустой или пробельный заголовок | Возникает прикладная ошибка. |
| Отрицательное число автомобилей | Возникает прикладная ошибка. |
| Отрицательное число мотоциклов | Возникает прикладная ошибка. |

Используйте параметризованный, табличный тест или subtests минимум для двух допустимых и двух недопустимых числовых значений. Хотя бы один набор данных сформируйте программно, например диапазон от `-3` до `3`.

Отдельно напишите unit-тест `TextReportSaver`: с временным каталогом он должен проверить имя созданного файла и его содержимое. Не используйте `report.txt` в корне репозитория.

## Часть 2. Тесты взаимодействий с моками

Проверьте `ReportService` без файловой системы и доставки сообщений. Передайте ему моки, стабы или простые тестовые реализации `ReportSaver` и `ReportSender`.

Для одного корректного отчёта проверьте:

1. `ReportSaver` вызван ровно один раз и получил тот же отчёт.
2. `ReportSender` вызван ровно один раз и получил тот же отчёт и email получателя.
3. Сохранение произошло раньше отправки.

Используйте библиотеку моков, если она принята в выбранной экосистеме. Иначе создайте реализации, записывающие вызовы в список или счётчик. В этой части нельзя обращаться к настоящему файлу или email-клиенту.

Добавьте один негативный сценарий: например, при ошибке сохранителя отправитель не вызывается, либо пустой email не передаётся отправителю.

## Часть 3. Интеграционные тесты

Интеграционный тест проверяет несколько настоящих компонентов вместе. Он отличается от mock-теста тем, что зависимости тестируемого сценария не подменяются.

Создайте тест, который:

1. Создаёт временный каталог для отчётов.
2. Собирает объектный граф DI: настоящий `TextReportSaver`, безопасную реализацию `ReportSender` и `ReportService`. При использовании контейнера поднимите тестовый DI-контекст.
3. Обрабатывает корректный отчёт с фиксированными датой и временем.
4. Проверяет имя и содержимое созданного файла.
5. Проверяет, что безопасный отправитель получил ожидаемые данные.

Не подключайте реальный SMTP, сеть или внешние API. Безопасный отправитель может хранить факт и параметры доставки в памяти или писать сообщение в тестовый поток вывода.

Если используется DI-контейнер, добавьте отдельный тест, что он создаёт `ReportService` и разрешает все его зависимости. Это защищает от ошибок регистрации компонентов и несовпадения контрактов.

## Что сдавать

- Код DI-варианта из практики 3 с правками для тестируемости.
- Unit-тесты модели и файлового сохранителя.
- Mock-тесты `ReportService`.
- Хотя бы один интеграционный тест полного сценария.
- Команду запуска тестов в README проекта.

## Самопроверка

- [ ] Основа работы — DI-вариант из практики 3.
- [ ] Unit-тесты не используют внешнюю инфраструктуру.
- [ ] Есть параметризованный или табличный тест с программно сформированными данными.
- [ ] Mock-тест проверяет число, аргументы и порядок вызовов зависимостей.
- [ ] Интеграционный тест использует настоящий `TextReportSaver` и временный каталог.
- [ ] Интеграционный тест не обращается к реальной почте, сети или внешним API.
- [ ] При использовании DI-контейнера протестировано создание `ReportService` из контекста.
- [ ] Все тесты проходят одной командой.
